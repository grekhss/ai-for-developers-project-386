# Архитектура

Описание состояния проекта на конец реализации первой функциональности
(календарь встреч). Документ отвечает на вопрос «как устроено и почему», а не
«как запустить».

- Команды, соглашения и ловушки Mantine — в [`AGENTS.md`](./AGENTS.md).
- Обоснование и история шагов — в [`plan-first-feature.md`](./plan-first-feature.md).

Проверено на: 17 файлов в `src/`, 40 тестов в 6 файлах, `npm run check` и
`npm run build` зелёные. Стек: React 19, Mantine 9.6.3, dayjs, TypeScript 6
со `strict`, Vite 8, vitest 4, oxlint.

## 1. Что это

Одностраничное приложение: календарь встреч. Пользователь выбирает день, во
всплывающем окне выбирает слот, запись сохраняется через абстракцию доступа к
данным. Данные пока в памяти — бэкенд запланирован, под него уже подготовлен
шов: замена реализации не затрагивает ни компоненты, ни хуки.

## 2. Поток данных

```
main.tsx ── MantineProvider(dark) + DatesProvider(APP_LOCALE) ──> App
                                                                 │
        ┌────────────────────────────────────────────────────────┤
        │                                                        │
  MeetingCalendar                                        BookingModal
  (DatePicker)                                           (Modal + TimeGrid)
        │                                                        ▲
        │ onSelect(date)                                         │ time, onBook
        ▼                                                        │
 App: selectedDate, time ──────── onChangeTime ──────────────────┘
        │
        │ handleBook(draft) ──► void createBooking(draft)
        ▼
 useBookings(api) ──► BookingsApi ──► createInMemoryBookingsApi
        │
        └─► bookings ─► App.takenTimes ─► BookingModal disableTime
                │
                └─► bookings / error / loading ─► строки статуса под календарём
```

Ключевое: **Mantine не протекает наружу `components/`.** Наружу отдаются
строки `'YYYY-MM-DD'` и `'HH:mm'`, поэтому остальной код не зависит ни от версии
Mantine, ни от его внутреннего устройства.

## 3. Слои и правило зависимостей

| Слой | Файлы | Правило |
| --- | --- | --- |
| `lib/` | `date.ts`, `slots.ts`, `bookings/{types,api,inMemory}.ts` | Ноль React и ноль Mantine. Чистые функции и типы, тесты лежат рядом. |
| `hooks/` | `useBookings.ts` | Единственное место, которое оборачивает `lib` в React-состояние, и единственный мост к `BookingsApi`. |
| `components/` | `MeetingCalendar.tsx`, `BookingModal.tsx` | Только рендер. Пропсы на входе, доменных правил нет. |
| `App.tsx` | — | Только UI-состояние и раскладка. Не импортирует `@mantine/dates`. |

Зависимости строго односторонние: `App → components → lib`, `App → hooks → lib`.
Обратных импортов нет.

**Домен не дублируется.** «Можно ли в этот день записаться» — это
`lib/date.ts:34` (`isBookable`), а не проверка внутри компонента. «Как написать
дату по-русски» — `lib/date.ts:39` (`formatDateRu`). Если второму компоненту
понадобится то же самое, он импортирует из `lib/`, а не переписывает правило у
себя. Расширение правила идёт в ту же функцию: к выходным добавятся праздники и
дни без свободных слотов.

## 4. Контракты

Все даты и времена — **строки**, не `Date`-объекты (`src/lib/bookings/types.ts:7`):

```ts
Booking    { id: string; date: 'YYYY-MM-DD'; time: 'HH:mm' }
BookingDraft { date: 'YYYY-MM-DD'; time: 'HH:mm' }   // то же без id
DateRange  { from: 'YYYY-MM-DD'; to: 'YYYY-MM-DD' }  // обе границы включительно

BookingsApi {
  list(range: DateRange): Promise<Booking[]>    // возрастание по (date, time)
  create(draft: BookingDraft): Promise<Booking> // возвращает запись с присвоенным id
}
```

Строки вместо `Date` — по трём причинам:

1. этого требует `DateStringValue` в Mantine v9;
2. `new Date('YYYY-MM-DD')` разбирается как полночь UTC и в отрицательных
   часовых поясах показывает предыдущий день;
3. строки `'YYYY-MM-DD'` лексикографически упорядочены так же, как
   хронологически, поэтому `inMemory.ts:17` фильтрует и сортирует без `dayjs`.

Правило доступности дня тоже живёт в `lib` и обращается к трём независимым
функциям: `isPast` сравнивает по дням (`isBefore(dayjs(), 'day')`), а не по
точному времени, иначе сегодняшний день считался бы прошедшим в течение суток;
`isWeekend` — суббота и воскресенье; `isBookable` — их отрицание.

## 5. Решения, за которые пришлось заплатить

**`MeetingCalendar` — единственный компонент со `DatePicker`, а `Calendar`
использовать нельзя.** У `Calendar` нет выделения: `value` / `onChange`
унаследованы от DOM-пропсов корневого `div`, то есть типизированы как свойства
`div` и **молча ничего не делают**, потому что `<div>` не стреляет `change`.
Выделение есть только у `DatePicker`, `DateInput`, `DatePickerInput`.
`DatePicker` рендерит `Calendar` внутри себя, то есть является заменой drop-in.
Правило недоступных дней переворачивается в конвенцию Mantine на месте:

```tsx
const notBookable = (date: string): boolean => !isBookable(date);
<DatePicker excludeDate={notBookable} />
```

**Выбор слота живёт в `App`, а не в модалке** (`src/components/BookingModal.tsx:32`).
Очевидная версия — `useState` внутри модалки — упирается в
`react/set-state-in-effect`: сброс при смене даты пришлось бы делать в эффекте, а
правило его запрещает. Контролируемый пропс `time` сбрасывается прямо в
обработчике клика по дате (`src/App.tsx:44`), `key`-remount не нужен:

```tsx
onSelect={(date) => { setTime(null); setSelectedDate(date); }}
```

Побочная выгода: `BookingModal` всегда смонтирован и получает `date: string | null`,
где `null` означает закрыто, поэтому Mantine не теряет анимацию закрытия.

**Первичная загрузка объявлена инлайном в эффекте, а не вызовом `refresh`**
(`src/hooks/useBookings.ts:74`). Правило `react/set-state-in-effect` срабатывает
**транзитивно**: оно ругается на вызов функции, трогающей состояние, из тела
эффекта — даже если `setState` происходит после `await`. Отсюда флаг `cancelled`:
он же спасает от двойного вызова эффекта в `StrictMode`.

**`lastBooked` хранит `BookingDraft`, а не `Booking`** (`src/App.tsx:18`). Нужен
только для строки «Запись: …». У `Booking` нет времени создания, поэтому «самая
свежая» из отсортированного массива не выводится, а «последняя по дате» — это не
то, что записал пользователь.

**Проп `api` в `App` — не удобство, а необходимость** (`src/App.tsx:12`).
`lib/bookings/api.ts:19` экспортирует модульный синглтон; без подмены записи
утекают между тестами одного файла, слот оказывается `disabled`, `userEvent`
кликает по неактивной кнопке, `time` не выставляется, и тест падает по таймауту
`findBy`. Воспроизведено: с синглтоном падает тест «занятый слот в следующий раз
не выбирается».

**Фабрика, а не синглтон, в `inMemory`** (`src/lib/bookings/inMemory.ts:8`) — по
той же причине. Отдельный тест «не делит хранилище между вызовами фабрики»
фиксирует это намерение.

## 6. Точки расширения

| Задача | Что менять |
| --- | --- |
| Бэкенд | `lib/bookings/api.ts:19` — одна строка на HTTP-клиент с тем же интерфейсом. Компоненты и хуки не трогаются. |
| Праздники, дни без свободных слотов | `lib/date.ts:34` `isBookable`. |
| Другое рабочее время | `lib/slots.ts:2-8` (константы) или аргументы `generateTimeSlots`. |
| Горизонт списка записей | `src/hooks/useBookings.ts:11` `HORIZON_DAYS`. |
| Ручное обновление списка | `refresh` уже возвращается хуком (`useBookings.ts:52`), но UI его пока не вызывает — кнопка добавится без изменения хука. |
| Список всех записей (не только модалка) | `App.tsx` получает весь массив `bookings`; сортировка и фильтрация — его дело, а не компонентов. |

## 7. Известные ограничения

Это осознанные решения текущего объёма, а не недосмотры. Каждое — с ценой,
которую полезно знать до начала работы.

1. **Занятые дни не помечены в календаре.** Единственное место, где записи
   влияют на UI, — `disableTime` в модалке (`src/App.tsx:21`). Это решение из
   плана: «сводная строка под календарём, без маркеров на ячейках».
   Если понадобится подсветка, `MeetingCalendar` принимает `bookedDates` и
   `getDayProps` — **но** `selected` в `getDayProps` затирает выделение,
   вычисленное самим `DatePicker`, поэтому нужно
   `value === date || bookedDates.includes(date)`. Свой `disabled` в
   `getDayProps` передавать нельзя: он вычисляется раньше `excludeDate` и тихо
   его ломает.
2. **Горизонт 90 дней фиксирован и не связан с показанным месяцем.** Запись на
   4-й месяц вперёд не помечается занятым днём. Нужен `onMonthChange` в
   `MeetingCalendar` и диапазон из отображаемого месяца — правка хука и API.
3. **`inMemory.create` не проверяет конфликты.** Двойная запись на один слот
   возможна, `disableTime` защищает только UI. При появлении бэкенда уникальность
   должна проверяться сервером; `createBooking` уже кладёт ошибку в `error`, не
   бросая её наружу (`useBookings.ts:60`).
4. **Запись не переживает перезагрузку** — in-memory хранилище. Ожидаемо до
   бэкенда.

## 8. Тестовая стратегия

40 тестов: `date.ts` 10, `slots.ts` 4, `inMemory` 6, `useBookings` 5,
`BookingModal` 8, `App` 7 (сквозной сценарий). Тесты колоцированы в `src/`,
поэтому `tsc -b` проверяет их типы бесплатно, и ошибка типа в тесте роняет
`npm run check`.

Требования, каждое из которых уже стоило времени:

- **`MantineProvider` обязателен** в дереве каждого render-теста — Mantine v9
  бросает `MantineProvider was not found in component tree`.
- **Нельзя проверять «сегодня выбирается».** Сегодня может быть выходным, и
  `[data-today]` станет неактивным. Тесты выбирают «первый доступный день
  показанного месяца» (`tbody button:not([disabled]):not([data-outside])`) и
  листают вперёд по `[data-direction="next"]`, если таких нет. Проверки правил
  делаются на `disabled`, а не на конкретных датах.
- **Локаль проверяется по `aria-label` дней** (`/^\d{1,2} [а-яё]+ \d{4}$/`), а не
  по заголовку месяца: заголовок показывает *текущий* месяц, поэтому тест на
  «октября» зелёный в октябре и красный в ноябре.
- **Классы в Mantine v9 — `mantine-DatePicker-*`, не `mantine-Calendar-*`.**
  Проверенные: `-weekday` (7 ячеек, lowercase «пн»…«вс»), `-weekdaysRow`,
  `-calendarHeaderLevel`, `-day`, `-monthTbody`.
- **Интеграционный тест обязан получить `api={createInMemoryBookingsApi()}`** —
  см. раздел 5.

Каждый новый тест проверен мутацией: с `takenTimes={[]}` и без
`setLastBooked(draft)` падают ровно два ожидаемых теста. Это дешевле, чем потом
отлаживать «зелёный, но ничего не проверяющий» тест.

## 9. Чек-лист инвариантов для агента

- [ ] `@mantine/dates` не появляется за пределами `components/` и `main.tsx`
      (в `main.tsx` — только `DatesProvider`).
- [ ] Доменное правило не переписывается в компоненте, а импортируется из `lib/`.
- [ ] `App` не начинает отдавать `Date`-объекты; наружу — строки.
- [ ] Не добавляется `useEffect` с `setState` и не вызывается из эффекта функция,
      которая его трогает.
- [ ] Новый render-тест обёрнут в `MantineProvider`, интеграционный — получает
      `createInMemoryBookingsApi()`.
- [ ] Каждый новый тест проверен мутацией.
- [ ] Пользовательский текст и комментарии — по-русски, `import type` для
      типов, точки с запятой как в редактируемом файле.
- [ ] Перед сдачей: `npm run check` и `npm run build`.

## 10. Проверки

```bash
npm run check   # oxlint && tsc -b && vitest run — единственный полный гейт
npm run build   # tsc -b && vite build
npm run lint    # линтер отдельно
npm test        # vitest run
```

`npm run dev` **не даёт обратной связи по типам**: Vite вырезает типы, не
проверяя их. Для проверки типов в разработке —
`npx tsc --noEmit -p tsconfig.app.json --watch` во втором терминале.

Линтер — `oxlint`, не ESLint. В `.oxlintrc.json` категории `correctness` и
`suspicious` это `error` и роняют код выхода, `perf` — `warn`, поэтому текущие
warning `react-perf` на инлайн-обратчиках и свежем массиве `takenTimes` падением
не считаются. `unicorn` в `plugins` отсутствует и потому выключен: `plugins`
заменяет набор по умолчанию, а не дополняет его.
