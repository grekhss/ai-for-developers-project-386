# План: модальное окно со слотами времени

**Статус:** выполнено. Реализация в коммите `5a630a3` (3 октября 2026).
**Цель:** клик по дате в календаре открывает окно со свободными слотами времени.

Исправления после сдачи (сверка с `found-problems.md`) — в разделе
«Последующие исправления» в конце документа; цифры шагов относятся к `5a630a3`.

Документ остаётся как запись выполненной работы: что было решено, что
разошлось с первоначальным планом и почему. Описание кода и контрактов — в
[`ARCHITECTURE.md`](./ARCHITECTURE.md), команды и ловушки Mantine — в
[`AGENTS.md`](./AGENTS.md). Здесь их намеренно не дублируем.

## Развилка по объёму (решено с пользователем)

- В модальном окне — **только выбор слота**, без формы брони (имя/почта).
- Слоты **генерируются** из рабочего дня, не хардкодятся.
- Запись живёт **за швом `BookingsApi`** (`lib/bookings/api.ts`), пока
  реализация in-memory. Смена на HTTP — одна строка в `api.ts`.
- В календаре блокируются **прошедшие даты + выходные** (сб/вс).
- **Сводная строка под календарём, без маркеров на ячейках дней.**
  → Маркеры отложены осознанно, см. отклонение в Шаге 3.
- **Cleanup отложен** — мёртвые файлы шаблона, `index.html`, README.
  → Выполнен ранее этой работы: см. «Что осталось на потом».

## Важно: Mantine 9.6.3 API (проверено по node_modules)

Это главные грабли, из-за которых исходный черновик не собирается. Раздел
сохранён как есть — проверки делались по
`node_modules/@mantine/dates/lib/**/*.d.ts` и `.mjs`, и с тех пор API не
менялся. Полный список ловушек, включая те, что вылезли при написании тестов,
— в `AGENTS.md`.

1. **Выделение даты — через `DatePicker`. `Calendar` использовать нельзя.**
   У `Calendar` есть только `date` / `defaultDate` / `onDateChange` — это
   **отображаемый месяц**, а не выделение. `value` / `onChange` у него
   унаследованы от DOM-пропсов корневого `div` (`ElementProps<'div'>`), поэтому
   выглядят валидными на уровне типов, но **молча ничего не делают**: `<div>`
   не вызывает `change`. Проверено:
   `node_modules/@mantine/dates/lib/components/Calendar/Calendar.d.ts`
   и `esm/components/Calendar/Calendar.mjs`.
   На этом уже споткнулся черновик: коммит `df6730b` «Fix issue with
   non-working date selection» заменил `Calendar` на `DatePicker`.
2. **`DatePicker` — рабочая замена:** он рендерит `Calendar` внутри себя и
   добавляет состояние выделения (`use-dates-state`). Пропсы
   `minDate` / `maxDate` / `excludeDate` / `renderDay` / `getDayAriaLabel`
   пробрасывает в `Calendar` как есть.

   ```tsx
   <DatePicker type="default" value={selectedDate} onChange={setSelectedDate} />
   ```

3. **Ловушка `getDayProps` — не затирать выделение.** `DatePicker.mjs:75-77`
   раскладывает сначала свои `getControlProps(date)` (там вычисляется
   `selected`), а поверх — `calendarProps.getDayProps?.(date)`. Значит
   пользовательский `selected` **заменяет** выделение самого `DatePicker`.
   Если помечаем занятые дни, объединять нужно вручную:

   ```tsx
   getDayProps={(date) => ({
     selected: selectedDate === date || booking?.date === date,
   })}
   ```

   Симметрично: `Month.mjs:85,89` — `disabled` вычисляется из `excludeDate` /
   `minDate` / `maxDate`, а `...dayProps` идёт **после**. Свой `disabled`
   в `getDayProps` перебьёт блокировку — не передавать.

   → В коде приёма нет: пометка занятых дней отложена (Шаг 3). Ловушка остаётся
   в силе на будущее — рецепт возврата в `ARCHITECTURE.md` §7.
4. **Тип значений — строки.** `DateStringValue = string` в формате `'YYYY-MM-DD'`
   (`types/GeneralTypes.d.ts`). `onChange` отдаёт `DateStringValue | null`
   (`PickerBaseProps.d.ts`), а `value` типизирован шире — `string | Date | null`
   (`DateValue`). Состояние хранить как `string | null`. Тип `Date` допустим
   для `minDate` / `maxDate` / `defaultDate`.
5. **`TimeGrid` уже есть** в `@mantine/dates` (v9) и создан ровно под эту задачу:
   `data: string[]` (`'HH:mm'`), `value`, `onChange`, `disableTime`,
   `minTime` / `maxTime`, `getControlProps`, `simpleGridProps`.
   Свои кнопки писать не нужно — приходят вместе с a11y и active-стилями.
6. **`DatesProvider` необязателен** (у контекста есть default), но default-локаль —
   `'en'`. Default `weekendDays: [0, 6]` совпадает с нашими сб/вс.

## Шаг 1 — `strict` и чистые функции в `src/lib/`

В плане шага не было, отдельного решения по `strict` тоже. Обоснование,
принятое при реализации: nullable date/time state — основной объём приложения,
и именно `strict` заставил явно сузить `null` в обработчике `DatePicker.onChange`
внутри `MeetingCalendar`.

Чистые функции — без компонентов, иначе сработало бы правило oxlint
`react/only-export-components`. Разделение по ответственности: `lib/date.ts` —
всё про даты, `lib/slots.ts` — всё про слоты. Типы записи живут отдельно в
`lib/bookings/types.ts`.

```ts
// src/lib/date.ts
export const APP_LOCALE = 'ru';                    // и им же настраивается DatesProvider
export function today(): string { /* 'YYYY-MM-DD' */ }
export function isWeekend(date: string): boolean { /* dayjs(date).day() === 0 || 6 */ }
export function isPast(date: string): boolean { /* isBefore(..., 'day') — иначе сегодня «прошедший» */ }
export function isBookable(date: string): boolean { /* !isPast(date) && !isWeekend(date) */ }
export function formatDateRu(date: string): string { /* dayjs(date).locale(APP_LOCALE).format('D MMMM YYYY') */ }

// src/lib/slots.ts
export function generateTimeSlots(
  startMinutes = 9 * 60,
  endMinutes = 18 * 60,
  stepMinutes = 30,
): string[] { /* '09:00' … '17:30' */ }
```

- Последний слот **начинается в 17:30**, чтобы встреча всегда заканчивалась
  к 18:00. Слот, который не помещается до конца рабочего дня, не выдаётся.
- `dayjs/locale/index.d.ts` объявляет модуль `dayjs/locale/*`, поэтому импорт
  русской локали проходит типизацию.
- `slots.ts` от dayjs не зависит вовсе — это арифметика минут, форматтера
  достаточно `padStart`.
- Чистые функции покрыты юнит-тестами рядом: `lib/date.test.ts` (10 тестов),
  `lib/slots.test.ts` (4) — без jsdom, мгновенно. В `date.test.ts` даты
  вычисляются от текущего дня, а не заданы константами: фиксированные даты рано
  или поздно уедут в прошлое, и тест начнёт врать.

**Отклонения от плана:**

- В эскизе выше не было `isBookable`, хотя Шаг 3 на него опирался. Функция
  добавлена — именно в ней правило должно жить, а не в компоненте.
- `APP_LOCALE` в эскизе объявлялся с пометкой «и им же настраивается
  DatesProvider»; в Шаге 4 того же плана предписывался литерал `locale: 'ru'`.
  Выбран первый вариант, литерал убран.

## Шаг 2 — Шов данных: `lib/bookings/*` и `hooks/useBookings.ts`

Отдельного шага в плане не было — только пункт в Развилке и упоминание
`types.ts` в Шаге 1. Без интерфейса `BookingsApi` обещание «смена на HTTP — одна
строка» не выполняется: и `MeetingCalendar`, и модалка, и `App` ходили бы в
in-memory напрямую.

Сделано: `types.ts` (`Booking`, `BookingDraft`, `DateRange`), `api.ts`
(интерфейс + экземпляр для приложения), `inMemory.ts` (фабрика), `useBookings.ts`.
Тесты: 6 на `inMemory`, 5 на хук.

**Отклонения от плана — все три решения пришлось принять по ходу:**

- **Фабрика, а не синглтон.** Иначе записи делятся между тестами одного файла,
  слот оказывается `disabled`, `userEvent` кликает по неактивной кнопке, и тест
  падает по таймауту `findBy`. Воспроизведено; есть тест «не делит хранилище
  между вызовами фабрики».
- **Первичная загрузка объявлена инлайном в эффекте, а не вызовом `refresh`.**
  Правило `react/set-state-in-effect` срабатывает транзитивно: ругается на вызов
  функции, трогающей состояние, из тела эффекта, даже если `setState` происходит
  после `await`. Отсюда флаг `cancelled`, он же спасает от двойного эффекта в
  `StrictMode`. В плане об этом правиле не было.
- **Горизонт списка — 90 дней от сегодня, фиксированно.** Планом не задумывался.
  Известный долг: он не связан с показанным в календаре месяцем, поэтому запись
  на четвёртый месяц вперёд не помечается занятым днём.

`refresh` хук возвращает, но UI его пока не вызывает — оставлена как готовая
точка для кнопки «Обновить».

## Шаг 3 — Извлечение `components/MeetingCalendar.tsx`

Шаг 3 исходного плана предполагал, что файл уже есть, и предписывал добавить в
него `bookedDates`. Файла не было: до коммита `5a630a3` в `src/` лежали четыре
файла, `DatePicker` рендерился прямо в `App.tsx`. Извлечение — часть решения
«`@mantine/dates` не протекает наружу `components/`», на котором держался весь
план по слоям.

Сделано: пропсы `value` / `onSelect`, `excludeDate={notBookable}`, сужение `null`
внутри `onChange`. `notBookable` вынесен в константу модуля, а не написан
инлайн-стрелкой, как в плане: предикат стабилен и не должен пересоздаваться на
каждом рендере.

**Отклонение:** `bookedDates` и `getDayProps` **не добавлены** — Развилка требовала
обойтись сводной строкой без маркеров на ячейках. Так не попал в код и второй
элемент ловушки `getDayProps` (свой `disabled` ломает `excludeDate`), то есть
две тонкости Mantine остались в графе неиспользованных кода и в ловушках
документации. Рецепт возврата с обеими оговорками — `ARCHITECTURE.md` §7.

## Шаг 4 — `components/BookingModal.tsx` (бывший Шаг 2)

Выбранный слот держит родитель, а не модалка: сброс при смене даты делается в
обработчике клика по дате, поэтому remount по `key` не нужен.

```tsx
interface BookingModalProps {
  date: string | null;                 // null — окно закрыто
  takenTimes: string[];                // занятые слоты дня, 'HH:mm'
  time: string | null;                 // выбранный слот
  onChangeTime: (time: string | null) => void;
  onBook: (draft: BookingDraft) => void;
  onClose: () => void;
}
```

Реализация:

- Импортировать `Modal`, `Button`, `Group`, `Text` из `@mantine/core`, `TimeGrid` из `@mantine/dates`.
- `Modal`: `opened={date !== null}`, `onClose={onClose}`, `size="sm"`, `centered`.
- Заголовок: `formatDateRu(date)`. Подпись: «Выберите время для встречи».
- `<TimeGrid data={SLOTS} value={time} onChange={onChangeTime} disableTime={takenTimes} />`,
  где `SLOTS = generateTimeSlots()` — модульная константа, слоты от состояния не зависят.
- Низ: кнопка «Отмена» (`variant="subtle" color="gray"` с `onClick={onClose}`) и кнопка «Записаться», `disabled`, пока не выбраны и день, и слот. Сборка черновика — одной функцией `toDraft(date, time)`, чтобы не проверять null дважды.
- `date` в типах остаётся `string | null`: при `null` окно просто закрыто.

8 тестов: русский заголовок, «не рендерится, если день не выбран», 18 слотов,
`disableTime`, наружу уходит выбранный слот, кнопка «Записаться» заблокирована
без слота и передаёт `{ date, time }`, «Отмена» зовёт `onClose`.

**Отклонения от плана:**

- Ранняя редакция шага держала слот в локальном `useState` модалки и сбрасывала
  его эффектом. Так нельзя: `react/set-state-in-effect` запрещает `setState` в
  эффекте, а remount по `key` — неявный приём без нужды. Отсюда контролируемый
  пропс `time`.
- Заголовок передаётся как `title={date === null ? null : formatDateRu(date)}`:
  под `strict` вызов с потенциальным `null` не проходит.
- Первая версия тестов упала целиком — Mantine v9 бросает `MantineProvider was
  not found in component tree`. Обёртка добавлена, ловушка записана в `AGENTS.md`.
- Тесты проверены мутацией: с убранными `disableTime` и `disabled={false}` падают
  ровно два соответствующих теста.

## Шаг 5 — Сборка в `src/App.tsx` (бывший Шаг 3)

Состояния — пять, а не два, как предполагал план:

- `selectedDate` — день, по которому открыта модалка;
- `time` — выбранный слот;
- `lastBooked` — `BookingDraft` последней сделанной записи, только для строки
  «Запись: …»;
- `bookings`, `loading`, `error` — из `useBookings(api)`. Собственное состояние
  записей в `App` не заводилось.

`takenTimes` считается из `bookings` для выбранного дня — это и есть единственное
место, где записи влияют на календарь.

Сводная строка под календарём (вместо прежнего «Выбранная дата: …») и четыре
плоских условия статуса: ошибка, загрузка, приглашение, сама запись. Нет
вложенных тернарников.

```tsx
<MeetingCalendar
  value={selectedDate}
  onSelect={(date) => { setLastBooked(null); setTime(null); setSelectedDate(date); }}
/>

<BookingModal
  date={selectedDate}
  takenTimes={bookings.filter((b) => b.date === selectedDate).map((b) => b.time)}
  time={time}
  onChangeTime={setTime}
  onBook={handleBook}
  onClose={closeModal}
/>
```

Фрагмент показан в текущем виде: сброс строки «Запись: …» в `onSelect` и
async `handleBook` добавлены после сдачи — см. «Последующие исправления».

**Отклонения от плана — четыре:**

- **`api?: BookingsApi` в `App`.** В плане не было вовсе, хук предполагался как
  `useBookings()`. Оказалось необходимостью: с модульным синглтоном падает тест
  «занятый слот в следующий раз не выбирается» — запись предыдущего сценария
  блокирует слот, клик не срабатывает, `findBy` виснет.
- **`lastBooked` вместо переменной `booking`.** План ссылался на `booking` без
  источника, и это не формальность: у `Booking` нет времени создания, поэтому
  «самая свежая» из отсортированного массива не выводится, а «последняя по дате»
  — не то, что записал пользователь. Хранится черновик, а не запись.
- **`loading` в списке состояний.** Планом не предусмотрен, показан как строка
  статуса.
- **`useBookings(api)` вместо `useBookings()`.** Следствие первого пункта.

Ранний вариант модалки в плане предлагал `key={selectedDate ?? 'empty'}` для
сброса слота — убран, слот сбрасывается в обработчике клика по дате.

## Шаг 6 — Локаль, тесты, проверки (бывшие Шаги 4, 4a, 5)

`main.tsx` обёрнут в `<DatesProvider settings={{ locale: APP_LOCALE }}>` — иначе
названия месяцев и дней недели рендерятся по-английски.

`App.test.tsx` переписан под новое поведение: 7 тестов вместо проверки
«Выбранная дата: …». Покрыты открытие окна, сценарий записи, отмена, повторное
открытие дня с уже занятым слотом, заголовок, локаль, блокировка недоступных
дней.

**Отклонения от плана — селекторы и три ловушки:**

- План советовал опираться на `[data-today]`. Отвергнуто: сегодня может быть
  выходным, и `[data-today]` станет неактивным. Тесты выбирают первый доступный
  день показанного месяца (`tbody button:not([disabled]):not([data-outside])`) и
  листают вперёд по `[data-direction="next"]`, если таких нет.
- План требовал проверять локаль по названию месяца. Заменено на `aria-label`
  дней и семь ячеек `-weekday`: заголовок показывает *текущий* месяц, поэтому
  тест на «октября» зелёный в октябре и красный в ноябре.
- План называл проверку заблокированных дней опциональной. Сделана обязательной и
  проверяет правило (`data-weekend` → `disabled`), а не конкретные даты.
- Классы в Mantine v9 оказались `mantine-DatePicker-*`, а не `mantine-Calendar-*`;
  weekday-метки в lowercase («пн»). Первая версия теста падала на несуществующем
  `.mantine-Calendar-header`. Обе находки — в `AGENTS.md`.
- Каждый новый интеграционный тест проверен мутацией: с `takenTimes={[]}` и без
  `setLastBooked(draft)` падают ровно два ожидаемых теста.

Факт на конец коммита `5a630a3`: `npm run check` — 6 файлов, 40 тестов, ошибок
линтера нет. Предупреждений `react-perf` — 6: пять на инлайн-обратчиках и один
на свежем массиве `takenTimes`. Уровень `perf`, не блокирует. `npm run build`
проходит. (Актуальные цифры после исправлений — в разделе «Последующие
исправления».)

4. **Оптимистичная запись в `handleBook`.** Раньше `setLastBooked(draft)` и
   `closeModal()` шли не дожидаясь результата `createBooking`: при падании
   создания пользователь увидел бы одновременно и красную ошибку, и синюю
   строку «Запись: …». С in-memory не воспроизводится, но сломалось бы сразу с
   бэкендом. Теперь `createBooking` возвращает `Promise<Booking | null>`
   (ошибка кладётся в `error` и возвращает `null`), `handleBook` async и ставит
   `lastBooked` только при успехе. Окно закрывается в любом случае — иначе
   ошибка остаётся под модалкой и не видна. Тест: неудачное создание не
   показывает строку «Запись».
5. **Коллизия id в `inMemory`.** `lastId = bookings.length` при сиде
   `[{id:'2'},{id:'3'}]` выдавал следующей записи уже занятый `'3'` — в тестах
   не воспроизводилось, сиды с id `1..3`. Считается максимум числовых id сида,
   есть тест на нестандартный сид.
6. **`lastBooked` не сбрасывался никогда** — строка «Запись: …» висела под
   календарём вечно: ни повторный клик по дате, ни отмена её не убирали.
   Зафиксировано решение: сброс одной строкой в `onSelect`, там же, где
   сбрасывается `time` — эффект не нужен. При закрытии окна строка остаётся —
   она показывает последнюю удачную запись. Тест: выбор другой даты убирает
   строку.

Итог: 40 → 43 теста (`inMemory` +1, `App` +2; в `useBookings` добавлены
ассерты на возвращаемое значение, счётчик файла не изменился). Мутации
проверены: откат `lastId` валит ровно новый тест `inMemory`; удаление
`if (created !== null)` — новый тест `App` на неудачное создание; удаление
`setLastBooked(null)` из `onSelect` — новый тест `App` на сброс. `npm run check`
(43 теста) и `npm run build` зелёные. Счётчики и мутации в `ARCHITECTURE.md`
§8 обновлены по факту замера.
